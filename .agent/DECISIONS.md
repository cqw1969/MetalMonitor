# DECISIONS（ADR）

## D-1 模拟数据发布形态（挂起，待部署场景评估时决）
背景：用户主张断线不得自动回退模拟数据，模拟数据或仅限 DEBUG 版
选项：A 显式化+改名"模拟数据（演示）"+二次确认 / B `#if DEBUG` 物理剔除
决定：挂起（用户："等到时候再做"）

## D-2 数据源能力缺失的处理分层（2026-10-21）
背景：串口/MQTT 不可用时的行为；空对象模式之争
选项：A 空对象模式（Null Object）/ B 原类 IsAvailable 状态标记 + 显式上报
决定：B——启动期 DI 注册缺失直接报错（GetRequiredService 抛异常）；运行期能力不可用经 IsAvailable 标记，统一上报错误中枢 + UI 变灰（STEP-4 落地 UI）
理由：空对象本质是静默，与"所有静默行为改 UI 提示"目标冲突；注册缺失是静态事实不值得做空对象
代价/风险：IsAvailable 需要各数据源服务逐一落地（STEP-2/3）；UI 降级依赖尚未实现的 IErrorReportService（STEP-4 挂起）
用户当时的判断：用户主动否定空对象（"会不会太过度设计"），提出"缺失依赖不一刀切启动失败，选项变灰徒留展示"；经联网验证（DI 缺失抛异常、空对象适用标准、fail-fast 实践）后确认方向正确

## D-3 IsAvailable 取值时机：动态计算（2026-10-21）
背景：SerialService.IsAvailable 需决定取值时机（STEP-2 子抉择）
选项：A 动态计算（每次访问实时 GetPortNames）/ B 构造时一次性快照
决定：A
理由：USB 串口热插拔是常态；快照把"能力"绑定到进程生命周期，与硬件变化的时间尺度错位；本机实测查询仅约 26 微秒/次，性能无忧
代价/风险：IsAvailable 是粗粒度信号（系统有无任意串口），不代表目标端口可用——细粒度由 ConnectAsync 端口预检兜底；热插拔瞬间连续两次读取值可能不同
用户当时的判断：用户以"答辩/面试演示不可接受重启才能刷新"为判据选 A，直觉命中快照语义与进程生命周期错位的建模缺陷，点评：判据抓得准
退场条件：若引入 VID/PID 绑定指定端口常驻监测（T4.3），IsAvailable 升级为按目标端口判断，本实现届时被替换

## D-4 数据源失败出口：三态状态面 + 事件（2026-10-22）
背景：取消"失败自动回退模拟数据"后，UI 失去失败判据，且 T4.1 断线三态、STEP-4 选项变灰都需要一个状态落点
选项：A 枚举三态（Online/Faulted/Unavailable）+ 变更事件；B 仅 LastDataSourceError 字符串；C 立即实现 IErrorReportService 错误中枢
决定：A
理由：B 无法驱动 UI 着色/变灰且运行中断线不可见，T4.1 还要返工；C 把尚未设计的错误中枢（分级、去重键、恢复语义）拖进 Core 层步骤，一次引入两个概念
代价/风险：State 为可变共享状态，约定"只在切源路径单写、事件广播后 UI 读"，不引入锁；与 T4.1 四态可能语义重叠，属可接受演进
用户当时的判断：用排除法排除 B（太简陋）与 C（太复杂），并对 C 的实际难度/职责做了追问；点评：排除法在工程选型中正当，判断成立
退场条件：STEP-4 落地错误中枢后，若中枢已能表达带来源的故障，DataSourceState 应退化为纯 UI 派生值

## D-5 故障期间不再生成模拟数据（2026-10-22）
背景：只取消"改写下拉框"不够——心跳生成条件原为 `!_useSerial && !_useMqtt`，故障时仍会造假数据掩盖中断
选项：A 生成条件改为"所选数据源 == 模拟数据"；B 保留原条件并额外用 State 判断
决定：A
理由：单一判据（用户选了什么）取代多旗标组合，表达式更短且不存在"故障时恰好满足"的组合；B 需要维护两处一致性
代价/风险：故障时曲线停更，用户若不知情可能误以为程序卡住——由三态事件 + 日志提示覆盖
用户当时的判断：在 STEP-3 申请中确认方案 A 包含此项
退场条件：无（本质是"降级不替换"原则的最小实现）
