# DECISIONS（ADR）

## D-1 模拟数据发布形态（挂起，待部署场景评估时决）
背景：用户主张断线不得自动回退模拟数据，模拟数据或仅限 DEBUG 版
选项：A 显式化+改名"模拟数据（演示）"+二次确认 / B `#if DEBUG` 物理剔除
决定：挂起（用户："等到时候再做"）

## D-2 数据源能力缺失的处理分层（2026-10-21）
背景：串口/MQTT 不可用时的行为；空对象模式之争
选项：A 空对象模式（Null Object）/ B 原类 IsAvailable 状态标记 + 显式上报
决定：B——启动期 DI 注册缺失直接报错（GetRequiredService 抛异常）；运行期能力不可用经 IsAvailable 标记，统一上报错误中枢 + UI 变灰（STEP-4 落地 UI）
理由：空对象本质是静默，与"所有静默行为改 UI 提示"目标冲突；注册缺失是静态事实不值得做空对象
代价/风险：IsAvailable 需要各数据源服务逐一落地（STEP-2/3）；UI 降级依赖尚未实现的 IErrorReportService（STEP-4 挂起）
用户当时的判断：用户主动否定空对象（"会不会太过度设计"），提出"缺失依赖不一刀切启动失败，选项变灰徒留展示"；经联网验证（DI 缺失抛异常、空对象适用标准、fail-fast 实践）后确认方向正确

## D-3 IsAvailable 取值时机：动态计算（2026-10-21）
背景：SerialService.IsAvailable 需决定取值时机（STEP-2 子抉择）
选项：A 动态计算（每次访问实时 GetPortNames）/ B 构造时一次性快照
决定：A
理由：USB 串口热插拔是常态；快照把"能力"绑定到进程生命周期，与硬件变化的时间尺度错位；本机实测查询仅约 26 微秒/次，性能无忧
代价/风险：IsAvailable 是粗粒度信号（系统有无任意串口），不代表目标端口可用——细粒度由 ConnectAsync 端口预检兜底；热插拔瞬间连续两次读取值可能不同
用户当时的判断：用户以"答辩/面试演示不可接受重启才能刷新"为判据选 A，直觉命中快照语义与进程生命周期错位的建模缺陷，点评：判据抓得准
退场条件：若引入 VID/PID 绑定指定端口常驻监测（T4.3），IsAvailable 升级为按目标端口判断，本实现届时被替换

## D-4 数据源失败出口：三态状态面 + 事件（2026-10-22）
背景：取消"失败自动回退模拟数据"后，UI 失去失败判据，且 T4.1 断线三态、STEP-4 选项变灰都需要一个状态落点
选项：A 枚举三态（Online/Faulted/Unavailable）+ 变更事件；B 仅 LastDataSourceError 字符串；C 立即实现 IErrorReportService 错误中枢
决定：A
理由：B 无法驱动 UI 着色/变灰且运行中断线不可见，T4.1 还要返工；C 把尚未设计的错误中枢（分级、去重键、恢复语义）拖进 Core 层步骤，一次引入两个概念
代价/风险：State 为可变共享状态，约定"只在切源路径单写、事件广播后 UI 读"，不引入锁；与 T4.1 四态可能语义重叠，属可接受演进
用户当时的判断：用排除法排除 B（太简陋）与 C（太复杂），并对 C 的实际难度/职责做了追问；点评：排除法在工程选型中正当，判断成立
退场条件：STEP-4 落地错误中枢后，若中枢已能表达带来源的故障，DataSourceState 应退化为纯 UI 派生值

## D-5 故障期间不再生成模拟数据（2026-10-22）
背景：只取消"改写下拉框"不够——心跳生成条件原为 `!_useSerial && !_useMqtt`，故障时仍会造假数据掩盖中断
选项：A 生成条件改为"所选数据源 == 模拟数据"；B 保留原条件并额外用 State 判断
决定：A
理由：单一判据（用户选了什么）取代多旗标组合，表达式更短且不存在"故障时恰好满足"的组合；B 需要维护两处一致性
代价/风险：故障时曲线停更，用户若不知情可能误以为程序卡住——由三态事件 + 日志提示覆盖
用户当时的判断：在 STEP-3 申请中确认方案 A 包含此项
退场条件：无（本质是"降级不替换"原则的最小实现）

## D-6 有界日志集合的归属与容量（2026-10-23）
背景：AlarmLogs 为 ObservableCollection<string> 只进不出，长时间运行无界增长；WPF 虚拟化只约束渲染、不约束存储
选项：A ViewModel 内私有 AddAlarmLog 方法（纪律约束，改 6 处调用点） / B 子类化 ObservableCollection 重写 InsertItem（机制约束，调用点零改动）；归属另有 UI 与 Core 两种
决定：方案 B；类型放 MetalMonitor.core/Collections/，容量 200，配 3 个单测
理由：机制优于纪律（新增日志入口无法绕过上限）；ObservableCollection 属 BCL，不引入 UI 框架依赖；放 Core 可获得单测覆盖；项目已有先例（RollingFileLogger 同住 Core 而 Core 自身不使用）
代价/风险：Core 承载一个自身不消费、仅 UI 使用的类型，包语义略不纯；容量策略（200）与集合实现分居两层
用户当时的判断：用户两轮坚持"Core 像后端、可承载基础设施"，并援引"日志数据本应源于 Core"；拒绝 UI 版的核心顾虑是领域层纯粹性。判断有合理基础（先例成立），采纳
退场条件：Core 需作为独立包对外发布 / 出现第二个消费者且裁剪策略不同（如按字节而非按条数） / Core 被要求执行零 UI 语义规范

## D-7 sealed 修饰符使用约定（2026-10-22）
背景：全项目 38 个类仅 2 个 sealed（FrameRouter、DataSourceStateChangedEventArgs，为此前会话随手所写而非约定），5 个同族 EventArgs 只有一个被封，同族不同待遇
选项：A 全量封（除 XAML/测试类，约 30 文件机械改动） / B 最小闭环 + 约定 / C 维持现状
决定：方案 B 变体——EventArgs 派生类立即统一 sealed（本批 4 个，STEP-6）；纯数据模型类与服务实现类按"所属任务验收 DONE 时封存"规则逐个处理；XAML 代码隐藏与测试类遵循框架惯例不加
理由：sealed 的主要价值是设计意图声明而非性能（无 virtual 成员的类性能收益为零，且 .NET 7+ 动态 PGO 进一步稀释）；约束的价值在模块定稿时最高，开发期结构仍在演化；避免大批量机械改动
代价/风险：sealed 状态在若干任务周期内不整齐，靠"验收时封存"规则防漂移
用户当时的判断：用户主动选择 B，理由"sealed 是封存/约定产物，项目仍在开发未到封存地步，一次改动多个文件直觉上排斥"——时机判断与变更成本直觉均正确；漏判的漂移风险以"验收时封存"规则补上
退场条件：若引入需运行时生成子类的机制（EF Core 代理、Moq 类 mock、AOP 框架），对应类立即拆封并在此记录

## D-8 链路健康判据：双时间戳区分"无字节"与"无有效帧"（2026-10-24）
背景：串口无底层心跳，单一阈值无法区分"线断了"与"有字节但全是乱码"
选项：A 仅按"无有效帧"判定 / B 仅按"无任何字节"判定 / C 双时间戳多态（Inactive/Healthy/NoValidFrame/NoSignal）
决定：C
理由：两类静默的排查动作不同（查线/供电 vs 查波特率/干扰/固件）；业界同类做法：OPC UA StatusCode 区分 BadCommunicationError 与 UncertainLastUsableValue，Modbus 主站库把超时与 CRC 错误列为不同异常
代价/风险：需维护两个时间戳（跨线程，用 Interlocked 读写 ticks）+ 一个纯函数评估器；3 秒阈值需实测微调，板子复位时会短暂误报
用户当时的判断：主动指出"没有有效帧和压根收不到数据是两种情况"，并追问业界主流；判断正确，原 A/B 二选一属于建模过粗
退场条件：改用自带链路状态上报的协议（Modbus TCP / MQTT keepalive 等）后，评估器退化为协议状态的映射

## D-9 连接结果与链路健康双维度（独立 LinkHealth + UI 两行并列）（2026-10-24）
背景：T4.1 需要表达"正常/中断/重连中"，现有 DataSourceState 只表达连接结果
选项：A 扩展 DataSourceState / B 独立 LinkHealth 枚举 + 新事件
决定：B；UI 以"数据源状态"与"链路健康"两行并列展示，不合并成"或"
理由：两个维度正交；Faulted（连接失败）与运行中断在时间线上是先后关系，强行并列会误导排查方向；SCADA 体系一贯把连接状态与标签质量分层表达
代价/风险：UI 需订阅第二套事件；LinkHealth 增加 Recovering 后，状态组合与优先级需写死（链路健康优先于连接结果展示）
用户当时的判断：用户选 B 并主张同时显示；经指出"Faulted 与中断几乎不会同时成立"后，接受两行并列；点评：正交拆分的方向正确，显示方式需工程化收口
退场条件：错误中枢（IErrorReportService）上线后，若其已能表达"来源 + 故障类型 + 恢复"，LinkHealth 事件可并入中枢，本枚举退化为中枢的派生视图

## D-10 每指标时间戳与质量码（落在 Device 层）（2026-10-24）
背景：断线时若只做链路级提示，无法表达"哪些设备的哪些值已不可信"
选项：A Device 层 per-metric 时间戳 + MetricQuality{Good,Stale,Bad} / B 仅 DeviceService 全局 LastValidFrameAge
决定：A
理由：单设备/单指标故障不应导致整系统显示失效；能表达"温度新鲜、压力陈旧"的混合状态；贴合既有约束"设备指标应附加时间戳与质量码"
代价/风险：Device 模型与卡片绑定改动；心跳需按设备×指标遍历（量级小，成本可忽略）；质量变更需按跃迁通知，避免 PropertyChanged 风暴
用户当时的判断：用户以"一台设备出问题不应该让系统报废，显示到具体设备才能及时修复"为由选 A；判断成立
退场条件：指标规模升至数千级时，改为按设备汇总质量 + 按需计算单指标

## D-11 重连定位：端口名优先，VID/PID 后置为优化项（2026-10-24）
背景：拔插或换 USB 口后 COM 号可能变化，需决定自动重连的寻址方式
选项：A 按上次端口名（指数退避 + 抖动）/ B 按 VID/PID 重定位
决定：A 为 T4.1 主路径；B 作为后续独立优化 STEP，仅在"端口名连接失败 + VID/PID 唯一匹配"时尝试
理由：VID/PID 在业界是辅助识别而非主路径（Arduino IDE、Linux udev 均如此）；CH340 的 VID/PID 通用（1A86:7523），多块同型号板无法区分；WMI 查询有延迟
代价/风险：换口后需用户手动重选端口；重连循环与用户主动切源存在竞争，必须用取消令牌收口，否则出现"已切走仍在偷偷连串口"
用户当时的判断：用户定"端口名缺省 + B 后置，若过于麻烦可完全延后"；排序判断正确
退场条件：现场确认存在多设备频繁换口场景时，再评估 B；若 B 被证实无法区分多板，整体弃用

## D-12 Recovering 的落地口径（2026-10-24）
背景：LinkHealth 需要五态（D-8/D-9），但"重连中"在 STEP-9 尚无重连逻辑可产；若只留枚举成员会变成死代码
选项：A Recovering=已连接但一个看门狗周期内尚未收到任何字节（等待首帧）；B Recovering 仅留给 STEP-11 的重连过程，STEP-9 暂不引入该成员
决定：A（STEP-9 由连接事件即可产出，非死代码；STEP-11 重连成功后同样落回该状态）
理由：连接成功 ≠ 链路可用，等待首帧是可观测的真实中间态；与 D-8 的"两类静默"判据自然衔接
代价/风险：连接瞬间若字节先于连接事件到达，会被清零并短暂显示 Recovering，下一帧自愈；"重连中"的语义在 STEP-11 需与"连上等首帧"共用同一枚举值
用户当时的判断：STEP-9 变更预览中已标"⚠️ 我替你定了"，用户确认方案 C 时未提出异议
退场条件：STEP-11 若需要独立的"重连退避中"状态（未连接但正在重试），应新增 Reconnecting 而非复用 Recovering
