# DECISIONS（ADR）

## D-1 模拟数据发布形态（挂起，待部署场景评估时决）
背景：用户主张断线不得自动回退模拟数据，模拟数据或仅限 DEBUG 版
选项：A 显式化+改名"模拟数据（演示）"+二次确认 / B `#if DEBUG` 物理剔除
决定：挂起（用户："等到时候再做"）

## D-2 数据源能力缺失的处理分层（2026-10-21）
背景：串口/MQTT 不可用时的行为；空对象模式之争
选项：A 空对象模式（Null Object）/ B 原类 IsAvailable 状态标记 + 显式上报
决定：B——启动期 DI 注册缺失直接报错（GetRequiredService 抛异常）；运行期能力不可用经 IsAvailable 标记，统一上报错误中枢 + UI 变灰（STEP-4 落地 UI）
理由：空对象本质是静默，与"所有静默行为改 UI 提示"目标冲突；注册缺失是静态事实不值得做空对象
代价/风险：IsAvailable 需要各数据源服务逐一落地（STEP-2/3）；UI 降级依赖尚未实现的 IErrorReportService（STEP-4 挂起）
用户当时的判断：用户主动否定空对象（"会不会太过度设计"），提出"缺失依赖不一刀切启动失败，选项变灰徒留展示"；经联网验证（DI 缺失抛异常、空对象适用标准、fail-fast 实践）后确认方向正确

## D-3 IsAvailable 取值时机：动态计算（2026-10-21）
背景：SerialService.IsAvailable 需决定取值时机（STEP-2 子抉择）
选项：A 动态计算（每次访问实时 GetPortNames）/ B 构造时一次性快照
决定：A
理由：USB 串口热插拔是常态；快照把"能力"绑定到进程生命周期，与硬件变化的时间尺度错位；本机实测查询仅约 26 微秒/次，性能无忧
代价/风险：IsAvailable 是粗粒度信号（系统有无任意串口），不代表目标端口可用——细粒度由 ConnectAsync 端口预检兜底；热插拔瞬间连续两次读取值可能不同
用户当时的判断：用户以"答辩/面试演示不可接受重启才能刷新"为判据选 A，直觉命中快照语义与进程生命周期错位的建模缺陷，点评：判据抓得准
退场条件：若引入 VID/PID 绑定指定端口常驻监测（T4.3），IsAvailable 升级为按目标端口判断，本实现届时被替换

## D-4 数据源失败出口：三态状态面 + 事件（2026-10-22）
背景：取消"失败自动回退模拟数据"后，UI 失去失败判据，且 T4.1 断线三态、STEP-4 选项变灰都需要一个状态落点
选项：A 枚举三态（Online/Faulted/Unavailable）+ 变更事件；B 仅 LastDataSourceError 字符串；C 立即实现 IErrorReportService 错误中枢
决定：A
理由：B 无法驱动 UI 着色/变灰且运行中断线不可见，T4.1 还要返工；C 把尚未设计的错误中枢（分级、去重键、恢复语义）拖进 Core 层步骤，一次引入两个概念
代价/风险：State 为可变共享状态，约定"只在切源路径单写、事件广播后 UI 读"，不引入锁；与 T4.1 四态可能语义重叠，属可接受演进
用户当时的判断：用排除法排除 B（太简陋）与 C（太复杂），并对 C 的实际难度/职责做了追问；点评：排除法在工程选型中正当，判断成立
退场条件：STEP-4 落地错误中枢后，若中枢已能表达带来源的故障，DataSourceState 应退化为纯 UI 派生值

## D-5 故障期间不再生成模拟数据（2026-10-22）
背景：只取消"改写下拉框"不够——心跳生成条件原为 `!_useSerial && !_useMqtt`，故障时仍会造假数据掩盖中断
选项：A 生成条件改为"所选数据源 == 模拟数据"；B 保留原条件并额外用 State 判断
决定：A
理由：单一判据（用户选了什么）取代多旗标组合，表达式更短且不存在"故障时恰好满足"的组合；B 需要维护两处一致性
代价/风险：故障时曲线停更，用户若不知情可能误以为程序卡住——由三态事件 + 日志提示覆盖
用户当时的判断：在 STEP-3 申请中确认方案 A 包含此项
退场条件：无（本质是"降级不替换"原则的最小实现）

## D-6 有界日志集合的归属与容量（2026-10-23）
背景：AlarmLogs 为 ObservableCollection<string> 只进不出，长时间运行无界增长；WPF 虚拟化只约束渲染、不约束存储
选项：A ViewModel 内私有 AddAlarmLog 方法（纪律约束，改 6 处调用点） / B 子类化 ObservableCollection 重写 InsertItem（机制约束，调用点零改动）；归属另有 UI 与 Core 两种
决定：方案 B；类型放 MetalMonitor.core/Collections/，容量 200，配 3 个单测
理由：机制优于纪律（新增日志入口无法绕过上限）；ObservableCollection 属 BCL，不引入 UI 框架依赖；放 Core 可获得单测覆盖；项目已有先例（RollingFileLogger 同住 Core 而 Core 自身不使用）
代价/风险：Core 承载一个自身不消费、仅 UI 使用的类型，包语义略不纯；容量策略（200）与集合实现分居两层
用户当时的判断：用户两轮坚持"Core 像后端、可承载基础设施"，并援引"日志数据本应源于 Core"；拒绝 UI 版的核心顾虑是领域层纯粹性。判断有合理基础（先例成立），采纳
退场条件：Core 需作为独立包对外发布 / 出现第二个消费者且裁剪策略不同（如按字节而非按条数） / Core 被要求执行零 UI 语义规范

## D-7 sealed 修饰符使用约定（2026-10-22）
背景：全项目 38 个类仅 2 个 sealed（FrameRouter、DataSourceStateChangedEventArgs，为此前会话随手所写而非约定），5 个同族 EventArgs 只有一个被封，同族不同待遇
选项：A 全量封（除 XAML/测试类，约 30 文件机械改动） / B 最小闭环 + 约定 / C 维持现状
决定：方案 B 变体——EventArgs 派生类立即统一 sealed（本批 4 个，STEP-6）；纯数据模型类与服务实现类按"所属任务验收 DONE 时封存"规则逐个处理；XAML 代码隐藏与测试类遵循框架惯例不加
理由：sealed 的主要价值是设计意图声明而非性能（无 virtual 成员的类性能收益为零，且 .NET 7+ 动态 PGO 进一步稀释）；约束的价值在模块定稿时最高，开发期结构仍在演化；避免大批量机械改动
代价/风险：sealed 状态在若干任务周期内不整齐，靠"验收时封存"规则防漂移
用户当时的判断：用户主动选择 B，理由"sealed 是封存/约定产物，项目仍在开发未到封存地步，一次改动多个文件直觉上排斥"——时机判断与变更成本直觉均正确；漏判的漂移风险以"验收时封存"规则补上
退场条件：若引入需运行时生成子类的机制（EF Core 代理、Moq 类 mock、AOP 框架），对应类立即拆封并在此记录

## D-8 链路健康判据：双时间戳区分"无字节"与"无有效帧"（2026-10-24）
背景：串口无底层心跳，单一阈值无法区分"线断了"与"有字节但全是乱码"
选项：A 仅按"无有效帧"判定 / B 仅按"无任何字节"判定 / C 双时间戳多态（Inactive/Healthy/NoValidFrame/NoSignal）
决定：C
理由：两类静默的排查动作不同（查线/供电 vs 查波特率/干扰/固件）；业界同类做法：OPC UA StatusCode 区分 BadCommunicationError 与 UncertainLastUsableValue，Modbus 主站库把超时与 CRC 错误列为不同异常
代价/风险：需维护两个时间戳（跨线程，用 Interlocked 读写 ticks）+ 一个纯函数评估器；3 秒阈值需实测微调，板子复位时会短暂误报
用户当时的判断：主动指出"没有有效帧和压根收不到数据是两种情况"，并追问业界主流；判断正确，原 A/B 二选一属于建模过粗
退场条件：改用自带链路状态上报的协议（Modbus TCP / MQTT keepalive 等）后，评估器退化为协议状态的映射

## D-9 连接结果与链路健康双维度（独立 LinkHealth + UI 两行并列）（2026-10-24）
背景：T4.1 需要表达"正常/中断/重连中"，现有 DataSourceState 只表达连接结果
选项：A 扩展 DataSourceState / B 独立 LinkHealth 枚举 + 新事件
决定：B；UI 以"数据源状态"与"链路健康"两行并列展示，不合并成"或"
理由：两个维度正交；Faulted（连接失败）与运行中断在时间线上是先后关系，强行并列会误导排查方向；SCADA 体系一贯把连接状态与标签质量分层表达
代价/风险：UI 需订阅第二套事件；LinkHealth 增加 Recovering 后，状态组合与优先级需写死（链路健康优先于连接结果展示）
用户当时的判断：用户选 B 并主张同时显示；经指出"Faulted 与中断几乎不会同时成立"后，接受两行并列；点评：正交拆分的方向正确，显示方式需工程化收口
退场条件：错误中枢（IErrorReportService）上线后，若其已能表达"来源 + 故障类型 + 恢复"，LinkHealth 事件可并入中枢，本枚举退化为中枢的派生视图

## D-10 每指标时间戳与质量码（落在 Device 层）（2026-10-24）
背景：断线时若只做链路级提示，无法表达"哪些设备的哪些值已不可信"
选项：A Device 层 per-metric 时间戳 + MetricQuality{Good,Stale,Bad} / B 仅 DeviceService 全局 LastValidFrameAge
决定：A
理由：单设备/单指标故障不应导致整系统显示失效；能表达"温度新鲜、压力陈旧"的混合状态；贴合既有约束"设备指标应附加时间戳与质量码"
代价/风险：Device 模型与卡片绑定改动；心跳需按设备×指标遍历（量级小，成本可忽略）；质量变更需按跃迁通知，避免 PropertyChanged 风暴
用户当时的判断：用户以"一台设备出问题不应该让系统报废，显示到具体设备才能及时修复"为由选 A；判断成立
退场条件：指标规模升至数千级时，改为按设备汇总质量 + 按需计算单指标

## D-11 重连定位：端口名优先，VID/PID 后置为优化项（2026-10-24）
背景：拔插或换 USB 口后 COM 号可能变化，需决定自动重连的寻址方式
选项：A 按上次端口名（指数退避 + 抖动）/ B 按 VID/PID 重定位
决定：A 为 T4.1 主路径；B 作为后续独立优化 STEP，仅在"端口名连接失败 + VID/PID 唯一匹配"时尝试
理由：VID/PID 在业界是辅助识别而非主路径（Arduino IDE、Linux udev 均如此）；CH340 的 VID/PID 通用（1A86:7523），多块同型号板无法区分；WMI 查询有延迟
代价/风险：换口后需用户手动重选端口；重连循环与用户主动切源存在竞争，必须用取消令牌收口，否则出现"已切走仍在偷偷连串口"
用户当时的判断：用户定"端口名缺省 + B 后置，若过于麻烦可完全延后"；排序判断正确
退场条件：现场确认存在多设备频繁换口场景时，再评估 B；若 B 被证实无法区分多板，整体弃用

## D-12 Recovering 的落地口径（2026-10-24）
背景：LinkHealth 需要五态（D-8/D-9），但"重连中"在 STEP-9 尚无重连逻辑可产；若只留枚举成员会变成死代码
选项：A Recovering=已连接但一个看门狗周期内尚未收到任何字节（等待首帧）；B Recovering 仅留给 STEP-11 的重连过程，STEP-9 暂不引入该成员
决定：A（STEP-9 由连接事件即可产出，非死代码；STEP-11 重连成功后同样落回该状态）
理由：连接成功 ≠ 链路可用，等待首帧是可观测的真实中间态；与 D-8 的"两类静默"判据自然衔接
代价/风险：连接瞬间若字节先于连接事件到达，会被清零并短暂显示 Recovering，下一帧自愈；"重连中"的语义在 STEP-11 需与"连上等首帧"共用同一枚举值
用户当时的判断：STEP-9 变更预览中已标"⚠️ 我替你定了"，用户确认方案 C 时未提出异议
退场条件：STEP-11 若需要独立的"重连退避中"状态（未连接但正在重试），应新增 Reconnecting 而非复用 Recovering

## D-13 自动重连的触发源：时钟驱动（2026-10-25）
背景：串口断线在 Windows/.NET 上大概率是静默的——`SerialService.ConnectionStateChanged` 只在主动 Connect/Disconnect 时触发，USB 拔出常不产生任何事件
选项：A 事件驱动（ConnectionStateChanged / SerialPort.ErrorReceived）/ B 时钟驱动（复用 1Hz 心跳，LinkHealth 进入 NoSignal 即触发）/ C 双保险（事件立即 + 时钟兜底）
决定：B
理由：串口无底层心跳，1Hz 看门狗已是唯一可靠的"缺席"发现者；再引入事件源会产生两个断线口径与并发竞态；B 是 C 的子集，若日后实测 3 秒延迟不可接受，再在 SerialService 挂 ErrorReceived 作为"提前叫醒"入口，属增量改动而非推翻。延迟可由既有配置键 Serial.WatchdogSeconds 调到 1 秒，无需改代码
代价/风险：发现延迟 = 看门狗周期（默认 3s）+ 首次退避（1s）；重连必须在心跳回调中发起，需用 Interlocked 旗标防重入，禁止每秒起新循环；仅在 NoSignal（无任何字节）时重连——NoValidFrame 说明线是通的，重连无益（应排查波特率/协议）
用户当时的判断：用户先以"拔线常常不触发"独立排除 A，再指出"重连本身需要时间可以理解"从而倾向 B，同时对 C 的性能与复杂度表示不确定；经解释后确认 B。点评：用可靠性证据排除 A、用需求本质（可恢复性而非零延迟）评估 B，两步判断都抓住了要害；对 C 的顾虑方向正确但需区分——性能代价趋近于零，真实代价是双触发源的竞态与测试组合翻倍
退场条件：现场要求恢复时间 <1 秒时升级为 C；改用自带链路状态上报的协议（Modbus TCP / MQTT keepalive）后，本机制退化为协议状态映射

## D-14 重连恢复加速路径与手动按钮的取舍（2026-10-26）
背景：STEP-11 B′ 落地指数退避无限重试后，有两条可选优化：① 端口重现即唤醒（插回线时重连循环立即跳出退避等待）；② 主屏加"立即重连"手动按钮。
选项：A 两条都做 / B 只做端口唤醒，不加按钮 / C 两条都延后
决定：方案 B，且端口唤醒留 STEP-12 实现
理由：① 按钮会掩盖参数错误——用户忍不住点说明退避曲线调错了，但按钮给了绕过出口，永远收不到"参数不对"信号；② 端口唤醒是 B 的增量（退避基建先到位，唤醒只需加每秒对比端口快照的逻辑 + CTS 提前触发），不推翻任何现有代码；③ 两个概念叠加（"重连循环" + "可取消延迟"）放在同一 step 会过载，用户节奏是一次只学一个；④ 业界成熟做法（Kepware Auto-Demotion、MQTTnet ManagedClient）也自动重连为主、手动入口深藏维护界面。
代价/风险：端口唤醒比"立即重连按钮"多一点复杂度（每秒对比快照 + 取消令牌协同），但测试网兜住后可控；在 STEP-12 之前，拔线较久再插回仍需等待退避窗口（最坏 30s、平均 15s）
用户当时的判断：用户主动表态"插回后立即重试"方向可取，但强调"太麻烦就留后续"；经评估复杂度后确认延后至 STEP-12。用户对按钮方案有疑虑（"会不会让自动重连变得不起眼"），被点评为方向正确但需更精确机理（掩盖参数错误、放错观众席）
退场条件：现场实测频繁出现"插回后还要等"的不爽，且 STEP-12 端口唤醒已落地仍不够快时，再考虑维护界面（非主屏）的手动重连入口

## D-15 设备详情页异步调用的收口范围（2026-10-28）
背景：DeviceDetailViewModel L77/L192 两处 `LoadXxxAsync().ConfigureAwait(false);` 无人 await。ConfigureAwait 是"等待"的修饰语，对未被 await 的调用零效果；且其返回值不是 Task，绕过 CS4014 警告；异常落入无人观察的 Task 后静默丢失。Loaded 事件只触发一次，只能接替构造函数那处，覆盖不了 setter 那处。
选项：A 最小收口（L192 搬到 Window Loaded await + L77 改 `_ =` 诚实火忘）/ B 完整生命周期（两处都搬到 View，ComboBox 加 SelectionChanged 的 async void）
决定：A
理由：切指标走本地 SQLite 查询，加载遮罩（XAML L139 已绑 IsLoading）已具备；B 需引入 SelectionChanged 与 SelectedItem 绑定顺序、启动期与 Activated 重复加载两处新风险，收益仅为"异常可查"。叠加当前处于术语学习过载期，优先保持主线节奏。
代价/风险：L77 保留火忘，异常仍只走 Console.WriteLine；快速连续切换指标存在"旧查询覆盖新结果"竞态，未根治；构造函数加载与 Activated→RefreshConfigsAsync 在启动期可能各查一次配置表，延后处理。
用户当时的判断：主动识别"术语密度超出当前学习承受度"，主张"最小化修复 + 立刻回主线 + 后续再优化"。点评：学习节奏判断正确；工程上"能收敛的先收敛、不确定的留待观测"同样成立。
退场条件：① 实测出现切指标数据错乱（竞态显形）；② 需要切换指标时显示加载遮罩；③ 启动期重复查库被实测确认有可感知延迟——任一出现即升级方案 B

## D-16 详情页指标列表刷新策略：增量同步替代 Clear+Add（2026-10-29）
背景：`RefreshConfigsAsync`/`InitializeAsync` 每次用 Clear()+逐项 Add 重建 `AvailableMetrics`。Clear 触发 ObservableCollection 的 Reset 事件，ComboBox 收到 Reset 后**延后**重建列表，STEP-15 补发的选中通知落在重建之前仍落空（error_fix_log #39 复发）。
选项：A Clear+Add 再叠加选中态重建手段（Dispatcher 延迟重发通知等）/ B 增量同步（同名更新、消失移除、新增插入，对象实例不离场）/ C 引入 DynamicData 等差量库
决定：B
理由：选中项对象从未离场，ComboBox 选中态天然保留，不依赖任何时序假设；6 项指标规模下 O(n²) 比对是微秒级，性能不构成选型依据，副作用才是。C 为一个下拉框引入第三方库不值。
代价/风险：同步代码比 Clear+Add 多约 30 行；`Insert(Math.Min(i, Count))` 护栏在 configs 含停用项时会让新项位置略偏后，仅影响显示顺序，不影响正确性。
用户当时的判断：先质疑"为一个下拉框思考这么久是否值得"，经多轮追问 Clear+Add 与增量同步的运行差异、O(n) vs O(n²) 量级、业界对应物（Android DiffUtil / React key）后，认清"选型依据是副作用而非性能"，确认 B。点评：从成本质疑切入、落到选型判据，推理链完整。
退场条件：指标数量升至百级且刷新频繁（比对成本可感知），或需要排序/过滤等更复杂的视图同步——任一出现即升级方案 C

## D-17 启动期连接失败的恢复策略：端口重现唤醒（2026-10-29）
背景：串口源启动时未接线 → 初始连接失败 → LinkHealth 停在 Inactive，永远达不到 MaybeStartReconnect 的 NoSignal 门槛，重连循环不启动；插线无任何反应，只能手动切源（真机实测）。
选项：A 初始失败也接入退避重连循环 / B 端口重现唤醒（轮询端口列表，目标端口出现即触发重连）/ C 维持现状 + 文档说明
决定：B（后经用户提议修订为"统一入口 TryStartReconnect + 可唤醒等待"形态：看门狗与端口哨兵共用一个入口，循环在跑时端口出现可提前唤醒并清零退避）
理由：演示关键场景是"开机发现没数据 → 插线 → 几秒内恢复"；A 最坏要多等一个 30 秒退避周期，观感不可接受；B 秒级响应。实施上不替代退避循环，引擎复用。
代价/风险：心跳每秒多一次 GetAvailablePorts 轮询（微秒级）；只认端口名——换 USB 口枚举成新 COM 号不唤醒（该缺口移交 D-18）；唤醒清零退避在端口抖动时可能激进。
用户当时的判断：量化演示场景等待成本（"插上还得等半分钟，印象不好"），并区分首次插线与运行期拔插两场景；随后主动指出"两个触发源不合并不够同构"及"运行期唤醒被防重入挡住"的缺口——批评成立，被采纳为修订设计。
退场条件：现场端口抖动风暴（端口反复闪现、连接尝试过密）→ 加唤醒冷却窗口；需识别"是哪块板" → 见 D-18 后续路径

## D-18 端口漂移应对：候选端口集合 + 被动协议匹配（2026-10-29）
背景：串口号随 USB 物理口/枚举变化漂移（COM5→COM7 实测发生），持久化单一端口名导致换口后永远连不上；演示场景手动改 config.json 不可接受。真实现状核查：串口只读上行（SerialService 无 Write/Send），NODE_ID 是路由地址非身份，CRC 只管帧完整性——**主动握手当前没有物理条件**。
选项：A 单端口回退（列表仅一个端口时直接试）/ B VID/PID 或 PNPDeviceID 设备指纹（需 WMI/SetupAPI 新依赖，且 CH340 类芯片多无唯一序列号）/ C UI 端口下拉框 / D-简 候选集合逐个试（无验证）/ D-全 候选集合 + 连接后被动监听验证 / E 主动握手（依赖 T5.x 下行命令通道，未建）
决定：D-全 + A 兜底
理由：零新依赖；候选集合自学习覆盖"换口"主场景；连上后监听一个验证窗口（复用 WatchdogSeconds≈3s），收到 CRC 通过且 NODE_ID 在路由表的帧才算成功，防"连错异类设备"；A 兜底首次全新端口。现场数据支持：演示机报错时端口列表仅一个端口；鼠标键盘为 HID 设备不占串口，干扰项不存在。
代价/风险：连接确认延迟一个验证窗口（约 3 秒，顶栏多显示一拍 Recovering）；被动匹配防不住"同固件同 NODE_ID 的另一块板"——**它不是身份认证**。
用户当时的判断：先质疑"COM 是动态分配的叫号，当匹配依据不好"（成立），上网查证工业标准流程（VID/PID → 序列号 → 固件握手）并逐层质问本项目对应能力，抓出"握手"一词的过度表述；最终接受"被动匹配是当前阶段最优裁剪"，并明确指定"身份检验为后续必要选项"。点评：查证—质疑—裁剪的推理链完整；对身份/路由/完整性三概念的区分已到位。
后续路径：真正的主动握手身份检验 = 用户指定的必要选项，挂在 T5.x 下行命令通道落地之后（上位机发查询命令，固件回应 DeviceId/序列号）
退场条件：验证窗口延迟在演示中不可接受 → 退 D-简；多板防伪需求出现 → 随 T5.x 实施 E

## D-19 设备身份模型：从"自定义握手帧"修订为"Modbus Read Device Identification"（2026-11-05）
背景：D-18 后续路径挂着"主动握手身份检验"，原设计是借用 Modbus 编号自定义 `CMD=0x2B/0x0E` 帧（AA 55 头 + 载荷）。D-20 确认走真 Modbus 后，设备自描述不再需要自定义帧，直接用 Modbus 标准功能码。
选项：A 自定义握手帧（CMD=0x2B 借用编号，载荷自定义）/ B Modbus Read Device Identification（0x2B/0x0E，标准对象结构）
决定：B
理由：标准功能码可被 Modbus Poll / 任意 Modbus 主站直接读取，零自定义协议；设备标识对象（厂商名/产品代码/版本号/序列号/能力位图）是 Modbus 规范的标准结构；与 D-20 的 Modbus 化合并实施，不额外增加帧类型；FrameParser 状态机零改动（不走 AA55 解析路径）。
代价/风险：固件需实现 Read Device Identification 响应（对象列表 + 分页）；上位机 NModbus 对 0x2B/0x0E 的支持需确认（NModbus 主站类可能不直接暴露，需发原始功能码请求）；设备标识字符串占用 Flash（C8T6 紧张，需控制长度）。
用户当时的判断：用户主张"一劳永逸且工业现实普遍的方法"+"只要能成事固件当然可以改"，认可主动握手方向；D-20 确认走 Modbus 后顺势用标准功能码。判断正确：用标准替代自定义是降复杂度而非增。

## D-20 通信协议升级路径：Modbus RTU → Modbus TCP，AA55 用条件编译保留（2026-11-05）
背景：当前自定义 AA55 推送协议无法解决端口漂移身份问题，且求职竞争力不足（工业现场事实标准是 Modbus）。用户目标：简历可写、能讲、能用，"顶多不实用或过度设计"。
选项：A 只做 Modbus RTU 从站（RS485/MAX485）/ B RTU + TCP 双传输（W5500）/ C 双协议并存（保留 AA55 + 加 Modbus 只读层）
决定：路径 = A → B（两段，C 不作为独立阶段）；AA55 不删除，固件用 `#define USE_AA55_LEGACY` 条件编译保留为回退保险。
理由：① B 是 A 的超集，复用同一份寄存器表，边际成本低；② C 与 A 实质重叠——A 的定义本就没要求删 AA55，A 做出来那一刻项目状态已是 C 描述的状态，C→A 是重复段；③ 条件编译比删除安全（已验证功能留作回退）且省 Flash（C8T6 64KB 紧张）；④ Modbus 是 1979 年 Modicon 公开的工业标准（Modbus Organization 维护），PLC/变频器标配，简历写"Modbus RTU/TCP 从站 + 上位机 NModbus 主站轮询"有事实支撑。
代价/风险：① C8T6 20KB SRAM 余量薄，硬约束不能加 FreeRTOS；② USB 供电需确认 W5500 冲击电流（建议加去耦电容）；③ 双传输 = 双份调试时间（RTU 的 3.5 字符判帧用 UART IDLE 中断；TCP 的 socket 状态机要自己管重连）；④ 上位机要从"被动收推送"改"主动轮询"，接缝必须守在数据入口层，业务层（StageSample/ApplyPendingSamples/EvaluateLinkHealthAt）一行不动；⑤ 简历风险：写"双传输"若被问 W5500 socket 重连机制答不出，比不写还伤。
退场/弃用条件：① C8T6 RAM 实测 >80% 或 W5500 供电连续卡住两轮调试 → 砍 TCP，只交 RTU；② 上位机轮询改造开始侵蚀业务层代码（需改 ApplyPendingSamples 等）→ 停，重新审视接缝设计；③ 时间紧到压缩验证（Modbus Poll 读不到就往下走）→ 砍 TCP。未验证的功能不写进简历。
用户当时的判断：用户识别出 B⊃A（B 是 A 的超集），选 B 为最终方案；并主动提出条件编译保留 AA55。点评：① 超集抽象正确；② 条件编译建议命中 C8T6 Flash 紧张的真实约束，比"直接删"更工程化；③ 漏判的是 C 与 A 的重叠（已在决定中合并）。
